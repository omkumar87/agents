Example: Offline Draft Persistence for the Compose Post Editor

Problem / context

Users lose an in-progress post draft when the app is killed by the OS or they lose network before hitting "Post." This is a top-5 support complaint on the compose screen.

Constraints

No noticeable typing latency, must work fully offline, minimal storage footprint, ships this sprint.

Options considered

A. Persist draft to Room on every keystroke, debounced 500ms.
B. Persist only on lifecycle events (onStop) via SavedStateHandle.
C. In-memory only — bet that process death is rare enough to ignore.

Tradeoffs

A survives process death and app-switching, at the cost of extra write I/O (mitigated by the debounce). B is simpler, but SavedStateHandle isn't durable across a real force-quit or the OS killing a long-backgrounded app — the actual failure mode in the complaint. C is simplest but doesn't solve the reported problem at all.

Decision

A — Room-backed, 500ms debounced autosave keyed by draft ID; clear the row on successful post.

Risks

A hard crash can still lose the last <500ms of typing — acceptable, since it matches "losing everything," not "losing a few characters," which is what users actually reported. Needs a new-table migration.

Example: Profile Screen Crash Loop After a StateFlow Migration

What happened

Migrated ProfileViewModel's LiveData to StateFlow + repeatOnLifecycle. Shipped Tuesday 2pm. Crash rate on the profile screen spiked from 0.1% to 4% within 30 minutes; rolled back at 2:40pm via feature flag.

Expected vs. actual

Expected a transparent swap with identical behavior. Actual: a deep-link path that navigates straight to Profile (skipping normal navigation) read viewModel.state.value before init finished, hitting a null case the old LiveData had tolerated silently.

Root cause (5 whys)

Crash → state accessed before init → deep-link path skips the normal init order → deep-link handling wasn't covered by the manual test pass → the test checklist didn't include deep-link entry points for screens under migration.

What I'd do differently

Add deep-link entry points to the manual regression checklist for any ViewModel migration; guard state access with a safe default instead of assuming an init order.

Action going forward

Added a "migration checklist" template that explicitly includes deep-link and process-death entry points, not just the normal navigation path.
